## Finding 1 — Every dylib load command kind counts

### What was wrong

`check-macho.py` only collected `LC_LOAD_DYLIB` (0xC) into `loads[]`. The other four
dylib-dependency command kinds — `LC_LOAD_WEAK_DYLIB` (0x80000018), `LC_REEXPORT_DYLIB`
(0x8000001F), `LC_LAZY_LOAD_DYLIB` (0x20), and `LC_LOAD_UPWARD_DYLIB` (0x80000023) — were
silently skipped, so a dylib carrying an extra weak or lazy dependency passed the check.

### Red test (fails on abe266c)

`test_rejects_extra_weak_or_reexport_load` — parametrised over the four non-standard kinds.
Builds a fixture with the standard libSystem dependency plus one extra entry using the
non-0xC command kind; asserts `returncode != 0` and `"extra"` or `"dependency"` in stderr.

**Red run (before fix):**

```
5 failed, 21 passed in 1.85s

FAILED test_rejects_extra_weak_or_reexport_load[LC_LOAD_WEAK_DYLIB-2147483672]
FAILED test_rejects_extra_weak_or_reexport_load[LC_REEXPORT_DYLIB-2147483679]
FAILED test_rejects_extra_weak_or_reexport_load[LC_LAZY_LOAD_DYLIB-32]
FAILED test_rejects_extra_weak_or_reexport_load[LC_LOAD_UPWARD_DYLIB-2147483683]
FAILED test_rejects_minos_above_floor  (finding 2, counted here)
```

### Fix (`packaging/engine/check-macho.py`)

- Defined `_DYLIB_DEP_CMDS = frozenset({0xC, 0x80000018, 0x8000001F, 0x20, 0x80000023})`
  and `_DYLIB_CMD_NAMES` for error messages.
- Changed name-extraction guard from `cmd in (0xD, 0xC)` to
  `cmd in frozenset({0xD}) | _DYLIB_DEP_CMDS`.
- Changed `loads.append(name)` to `loads.append((cmd, name))` — now a list of `(cmd, name)` pairs.
- After the loop: split `loads` into `bad` (non-0xC) and `good` (0xC). `bad` raises immediately,
  naming the command kind. `good` must equal `["/usr/lib/libSystem.B.dylib"]`.
- The policy: `LC_LOAD_DYLIB` 0xC is the only permitted kind; any other kind is a rejection, even
  if the name would otherwise be acceptable.

## Finding 2 — macOS floor enforced

### What was wrong

`check-macho.py` read `minos` and printed it but never validated it against the 13.0 floor.
A dylib built against macOS 14.0 SDK passed without complaint.

### Red test (fails on abe266c)

`test_rejects_minos_above_floor` — builds a fixture with minos packed as `14 << 16` (14.0.0);
asserts `returncode != 0` and `"14"` in stderr.

Also added `test_real_dylib_minos_exact` — parametrised over both real dylibs; asserts
`"minos 13.0.0"` appears literally in stdout. This test **passes on abe266c** (the real dylibs
are already 13.0.0); it is a tightened regression guard rather than a red gate.

**Red run (combined, before fix):** 5 failed as shown in Finding 1 above.

### Fix (`packaging/engine/check-macho.py`)

- Added `_MINOS_FLOOR = 13 << 16`.
- After decoding `minos_raw`, added:
  ```python
  if minos_raw > _MINOS_FLOOR:
      raise ValueError(
          f"minos {minos} exceeds the macOS 13.0 floor; rebuild against the correct SDK"
      )
  ```
  Error message includes the actual `minos` string (e.g. `"minos 14.0.0 exceeds…"`), satisfying
  the requirement to name the actual value.
